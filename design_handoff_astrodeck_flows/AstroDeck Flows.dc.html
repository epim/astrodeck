DESIGN NOTES — FLOWS
Grounding. A flow compiles 1:1 to what the engine already runs: the flow lane is a SequencePlan (targets → slew/center → autofocus → guide → exposure steps → report), and amber event wires are the Instruction grammar (when-trigger-do-action: on_hfr_above, on_guide_rms_above → notify / refocus / abort). No node invents a capability the server lacks.
Port grammar. Cyan = control flow; exactly one run cursor travels it. Amber = events; they can fire at any time while the flow runs. Kind mismatches refuse to wire and say why.
Shape, not color. Status LEDs keep the app's silhouettes (dash = idle, sweep = busy, check = ok, halo = warn, square = alarm); the simulator badge stays dashed-with-hollow-dot. Everything survives the night LUT.
Night mode here is approximated with a red LUT over the whole surface — the shipped app swaps the full token ladder with measured AA contrast per rung.
Phone. Three bottom tabs. CANVAS is the same read/write graph with compact nodes — drag, wire, pinch-to-zoom. LIST is the graph linearized for gloved one-thumb use: the flow rail plus when▸then rule trees. MONITOR runs the night. Params and RUN are full-fidelity everywhere; LIST stays the calmest way to edit in the dark.
Open questions. Mosaic panels as a node or a Target detail? Should a live-stack sink appear before the engine ships it? Parallel target lanes vs. the scheduler's own ordering?
