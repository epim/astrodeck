01  the walls

every box wants to be the whole sky.

Buy an ASIAIR and you buy a wall. It drives ZWO gear beautifully and everything else not at all. Run NINA on a mini-PC and you get power, but you’re married to Windows and a sprawl of plugins. Each ecosystem assumes it owns the mount, the camera, the night.

AstroDeck refuses that bargain. The hard truth: no single vendor talks to all your hardware — so the controller has to.

Vendor lock-in

A closed app speaks one brand. Mixed gear — a Pegasus focuser, a QHY camera, a third-party mount — falls outside the garden walls.

The ASIAIR ceiling

Polished, but sealed. You drive what they support, the way they support it. No seam to extend, nothing to own.

The NINA bridge

Capable and open-ish — a perfect transition. But it’s a Windows host with its own profiles, and it shells out to phd2.exe by hand.

AIM

NINA is treated as a bridge, not a destination. The end-state is no-NINA: talk ASCOM Alpaca and native drivers directly. Every feature is built against one device abstraction so the bridge can be swapped out from under it without the UI ever noticing.

02  the plugin seam

a backend is a module + one line.

The whole design rests on a tiny, already-committed contract in devices/backend.py. Choosing Simulator / NINA / Native / PHD2 for a device is data, not an if/elif chain buried in the hub.

Three nouns carry everything:

  • ConnSpec — how to reach one role on one backend. The persisted, replayable unit: backend, optional host/port/dev_num, and an open extra dict. Round-trips to JSON.
  • Backend / BackendSession — a backend is a stateless factory; open() returns a live session that hands out devices per role plus an optional native guider, native solver, and a health probe.
  • The registry — register(b), get_backend(name), list_backends() over one dict. That dict is the entire plugin surface.

drop a file under devices/backends/ · call register() at import · the hub never learns its name

SEAM

A new backend filling an existing role = a new module + one register() call (and one honest import line in backends/__init__.py). Zero hub edits. The hub imports the registry and the active rig plan — nothing else. This is exactly what lets the future Rust and INDI drivers land without touching the core.

03  primary + per-role overrides

pick a primary. override one role.

A whole rig is a RigSpec: a primary backend that fills every role by default, plus a dict of per-role overrides. Any role you don’t name inherits the primary. The guider being independently pluggable today is just this model with one override — AstroDeck generalizes it to every role.

The headline case — a mixed rig you really fly:

native mount + camera · PHD2 guiding · roles sharing an endpoint share one session

TRUTH

REAL vs SIM is a per-role badge at every place you act — never one global “simulator” chip. A primary=sim rig with a real-mount override that lit a global “sim” chip while a real mount physically slewed would be a dangerous lie on the daytime bench. So the SlewPad, capture controls, and guide controls each read their own role’s backend, and a single loud header banner names any real motion device by name.

04  the orchestrator

bring the rig online — and degrade gracefully.

One function takes a RigSpec and assembles a live rig: connect_profile(). It resolves each requested role to a backend, groups roles by (backend, host, port) so each endpoint opens exactly one session, builds the devices, and picks the guider and solver.

  • One session per endpoint. Two native roles on the same Alpaca host share one connection; a different host opens a second. Sim roles always coalesce to one shared SimRig — stray addressing can’t split the simulated state.
  • Per-role tri-state result. Every requested role returns a RoleResult: connected / tried & failed (error) / never tried. A missing focuser never stops the camera coming up.
  • Teardown is leak-safe. If a later step raises, every session already opened is closed. On a profile switch, old sessions close before the new ones open — two generations of transports never coexist.

Boot, unattended — the safe defaults

On startup, if a profile is saved, the rig comes up with no click. The auto-connect swallows failures — a crash here would brick the whole UI — so the app always starts and reports a disconnected rig rather than a white screen.

SAFE

A real mount that comes up idle is left parked, tracking off. AstroDeck never auto-unparks, auto-slews, or enables tracking without an authenticated human action.

HALT

But if it finds a mount already tracking into the sun cone (a power blip mid-day), it stops tracking before showing any banner — halting unsafe motion it discovers is the deliberate exception to “never initiate motion.”

A persisted in-progress sequence never auto-resumes after a restart — it enters PAUSED · PENDING ACK, surfaced on the header chip and the escalation sink, resumable only behind a consequence-naming hold-confirm. And a hard sun-exclusion cone — independent of whether your site is even configured — sits at the mount-motion boundary, so sequence, polar, and meridian-flip re-slews all inherit it.

05  managed PHD2

stop hand-feeding phd2.exe.

The complaint with NINA is concrete: it shells out to phd2.exe and makes you hand-maintain a separate PHD2 equipment profile. Two sources of truth, drifting.

AstroDeck’s answer: own PHD2 as an internal supervised service behind the same Guider interface. When you ask for managed mode, the Phd2Backend gains a supervisor that:

  • Auto-launches phd2 --headless — shell=False, a fixed argv list, a path checked against an allowlist. User strings never become flags.
  • Syncs the equipment profile by writing the PHD2 store directly on disk — the registry on Windows, an INI/plist elsewhere — because PHD2’s JSON-RPC has no method to set the guide camera, mount, or pixel scale. No duplicate hand-kept profile.
  • Auto-connects, auto-selects a star, calibrates, and a watchdog restarts a crashed headless process on capped backoff — re-writing the profile and reconnecting.
GUARD

Two hazards are designed out. The pixel scale written is the guide camera’s, not the imaging train’s — conflating them makes guide RMS and dither wrong by the guidescope/mainscope focal ratio (often 3–5×). And managed PHD2 is incompatible-by-construction with a NINA rig — NINA already owns that :4400 process and its profile — so the picker hard-disables the toggle and the server refuses to clobber a PHD2 it detects already listening.

The true “no separate binary” end-state is a native in-process guider — that’s on the roadmap. Managed PHD2 is the graceful bridge until then.

06  who may drive

capabilities, not hardcoded checks.

A route declares the capability it needs. A role is just a bundle of capabilities. The capability set is built by walking every mutating route in the app, not from an abstract taxonomy — and the route→capability table is asserted at boot: if any control route lacks a declared capability, the app refuses to start.

viewer

view

Watches live status & preview. Drives nothing. UI renders read-only — motion controls are hidden, not 403-on-tap.

operator

view · control.capture · control.guide

Images and guides. Cannot start a slewing sequence — that’s motion, and motion needs control.mount.

admin

ALL_CAPS

Everything — motion, power, backend config, safety floors, alerts, users. Destructive caps double-confirm even for admins.

ESC?

The subtle part is the motion boundary. A sequence slews, centers, and meridian-flips per target; polar rotates RA; sequence/recover re-enters the same engine. So control.mount is re-derived from every route that transitively reaches a motion sink — not a hand-picked list — closing the leak where an imaging-only operator could quietly drive a real mount across the sky.

OPEN

The default provider is none: on your LAN, every caller is admin — no login, full control, byte-for-byte today’s behavior. Turn on the google provider (OIDC + PKCE, email_verified, an allowlist re-checked every request) and identity becomes real — same seam, different token validation. The home issues its own asymmetrically-signed session, so no shared secret can ever mint an admin token elsewhere.

07  remote access

at dinner. friends watching.

You’re out to dinner; the rig is imaging in the backyard. You want to check on it from your phone — and drop a link so a friend across the country can watch the subs roll in. No port forwarding, no exposing your LAN to the internet.

The home server dials outbound to a small cloud relay and holds a persistent gRPC stream open. Remote browsers reach the relay over HTTPS + grpc-web; the relay tunnels each request down to home and replays it against the home’s own app. The entire existing UI + REST + WS is tunnelled, not rewritten.

home dials out · relay brokers · RBAC enforced at relay AND home (defense in depth)

  • Scoped viewer links. A /share link mints a viewer-only session — no Google account, a separate signing key, a revocable jti, an explicit capability set. Friends watch; they never drive.
  • The relay is advisory; the home is authoritative. The relay tags each frame with a relay-signed principal, but every control route re-checks at home. A compromised relay can act as an already-authenticated viewer — it can never mint admin.
  • It can never break your LAN. The dial-out client is an isolated background task. A relay outage leaves local access 100% unaffected; bulk media (FITS/PNG) rides its own stream so it can’t head-of-line-block live guide events.
WHY

A custom relay was chosen over Tailscale / Cloudflare Tunnel precisely to own the auth boundary end-to-end — per-user role tagging, scoped viewer links, and a principal the home re-verifies. An off-the-shelf tunnel would expose the whole service with none of that control.

08  where the seam leads

every future is just another register().

Because the plugin seam exists, the roadmap costs no architecture. Each item below is additional Backend registrations — the UI and hub never learn the difference.

shipping now — the foundation

Pluggable harness · RBAC · cloud relay

The seam, four wrapping backends, managed PHD2, capability bundles + Google OIDC, and the tunnelling relay — built and verified in dependency order.

next — native in-process guider

NativeGuider — retire the binary

Multi-star centroiding on the guide camera + mount pulse_guide, behind the same Guider interface. The honest cost: it must re-implement calibration — the per-axis mount-response measurement PHD2 gives for free.

then — native & Rust drivers

INDI · native SDKs · the NINA→Rust port

Talk to ZWO / QHY / Pegasus through native or Rust-FFI backends where an SDK is faster, plus the deferred rotator, dome, and auto-flat CoverCalibrator roles. The bridge dissolves; the contract stays.

END

The destination was never “a better NINA front-end.” It’s a controller where your hardware, your software, and your access policy are all data you own — and the bridge to whatever you run today can be swapped out from under it without the night ever noticing.
