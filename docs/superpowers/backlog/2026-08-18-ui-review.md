# UI review: pressing everything, and what came back

2026-08-18, against 0.2.89 on the rig. Three questions, asked of every control:
can you tell it was clicked; does it show that something is in progress; and
when it fails, is the failure evident and clear as to why.

## How it was measured, and why that took five tries

Press feedback is a claim about PIXELS, so it is measured in pixels: the
control is screenshotted at rest, at hover, and with the mouse held down, and
the press is "visible" only if the hover and down images differ. Hover is
captured separately because a `:hover` style would otherwise be counted as
press feedback.

The harness was wrong five times before it was right, and every version
produced confident, false findings:

| # | Bug | What it reported |
|---|---|---|
| 1 | checked `role=dialog`; the app renders `alertdialog` | "the confirm never renders" |
| 2 | moved the mouse to a **cached** bounding box, then screenshotted (which scrolls) | **every control on the page** has no press feedback |
| 3 | collected element handles once per view; the first press re-renders React and detaches the rest | 47 of 129 controls "errored" |
| 4 | locators from `.all()` re-resolve under strict mode | the same 47, different cause |
| 5 | counted DISABLED controls as unresponsive | `PUSH NOW` flagged as broken — it is correctly disabled with no sync target |

Two more that were not the harness's fault but ruined runs anyway:

* **The relay is not a measurement surface.** Two browser sessions against it
  produced "8 controls on screen" and "0 controls on screen" for the same view
  on consecutive runs. The sweep moved to an SSH tunnel; the relay is still
  where relay-specific behaviour gets checked.
* **The session dies at 30 minutes** and the app falls back to the login
  screen. Every view after that reported "could not open" — a broken view and
  an expired cookie look identical from outside. The harness now says which.

## A mistake worth recording

The "safe to press" list was a filter on button TEXT. It let `+1°` through —
which is a rotator move, because the word "move" is in the handler's name and
not on the button. It moved the real rotator from 346.47° to 347.46°; restored
to 346.47° exactly, verified stationary.

An earlier press of the same control had returned 409, which read as "this
control is refused" and was really a transient.

**The fix is structural, not a longer word list:** the harness now blocks every
POST/PUT/PATCH/DELETE at the browser. Press feedback is a client-side question,
so it never needed the request to land. That makes all 169 controls safe to
press — including the 40 the text filter was holding back — and turns every
write into a failure case, which is what question 3 needs anyway.

## Results

172 controls across 15 views. 95 measured cleanly (the rest were disabled,
absent when revisited — several panels populate async — or lost to the last of
the harness bugs).

### 1. Can you tell it was clicked?

**15 controls changed nothing at all**, and they were one family: the chips,
cards and disclosure rows that opt out of `.btn`.

| where | controls |
|---|---|
| Settings | all 8 filename token chips — `$$TARGET$$`, `$$FRAMETYPE$$`, `$$FILTER$$`, `$$DATE$$`, `$$TIME$$`, `$$DATETIME$$`, `$$NIGHT$$`, `$$FRAMENR$$` |
| Flows | folder filters `All` / `My flows` / `Examples`, and the flow CARDS |
| Focus / Capture | exposure presets `6s g200`, `60s g120` |
| Capture | the `CAMERA PHOTOMETRY` disclosure |

FIXED in 0.2.90: a global `button:not(.btn):active { filter: brightness(1.35) }`.
`brightness`, not a transform — these are cards and inline chips inside dense
tables, where a nudge would shift text sideways under the finger. It is also
not motion (survives `prefers-reduced-motion`) and not a hue (survives the
night palette collapsing toward coral). Re-measured after deploy: **15 -> 0**.

Separately, `.btn:active` itself was one pixel of `translateY` with `transform`
absent from the transition list — about 80 ms of a one-pixel move. Fixed in
0.2.89 with three channels (nudge, inset shadow, accent border).

### 2. Does it show that something is in progress?

**20 of 95, and they are the right 20** — every slow, device-touching action
does it: the rotator nudges, ROTATE TO PA, SYNC TO SKY, START ALIGNMENT, HOME,
UNPARK, SOLVE & SYNC, SINGLE, LOOP, LIVE VIEW, BAHTINOV FOCUS, SET SITE, USE MY
LOCATION, USE MOUNT GPS, the SAVEs, REBUILD PREVIEWS, and opening a flow. No
gap found here.

### 3. When it fails, is it evident and clear?

**Yes.** With every write aborted at the browser, the UI reports
`network error — server unreachable`, placed next to the control that failed
and repeated inside any open modal. It names the cause rather than a code.

The one place it is NOT clear is the flow log strip, which renders below the
fold — see the open items.

## Still open

1. **The main pane overflows the viewport by ~112px.** Measured on Flows: the
   pane starts at y=118 with height 1044, bottom edge 1162 in a 1050-tall
   window. Anything anchored `bottom-0` inside it is off-screen, which is where
   the flow log strip lives — and why a refused RUN appeared to do nothing.
2. **The weather modal takes the whole console.** A full-viewport scrim at an
   arbitrary moment. A forecast is worth saying; it is not worth locking
   Equipment, Mount and Focus behind a dismissal.
3. **The relay drops constantly.** The event log shows dozens of
   `relay connection lost (1011 keepalive ping timeout); retrying local-only`
   between 04:10 and 07:33. This also made the relay useless as a measurement
   surface — the same view reported 8 controls and then 0 on consecutive runs —
   and it is the standing lead for the gallery-loading report.
4. **`could not read site from mount`** repeats every ~40 minutes, log-only.
5. **`bg_nebula.png` 404s** on every page load over the relay.
6. **A modal without `.overlay-scrim`.** FILTER SLOT NAMES traps the nav until
   dismissed; harmless once noticed, but it is the one modal that does not
   share the class everything else uses.
